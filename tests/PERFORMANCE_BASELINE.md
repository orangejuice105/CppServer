## 测量方式

- 独立 Release 构建，使用生产 `main()`、事件循环、路由、收发及关闭策略。每个请求重新建立 TCP 连接，读取并校验状态、响应头、完整正文及服务器 FIN。
- 保留生产 INFO 异步文件日志：队列容量 10000，批大小 100，单文件 10 MiB，最多 3 个归档。没有关闭日志，也没有扩大 backlog 或修改超时。
- 每种场景预热 0.5 秒，发压 3 秒，重复两次。统计时间包含最后一批在途请求完成的时间，因此实际测量时长可能超过 3 秒。延迟包括连接建立、完整响应、服务器发送方向关闭及本地连接清理。
- 同机回环网络，Python asyncio 客户端。AMD Ryzen 9 7940HX，进程 CPU affinity 为 32 个逻辑 CPU；文件描述符软硬限制均为 1048576。完整 Linux/WSL 环境及内存信息保存在 JSON 中。
- 测试 shim 映射临时端口，并对 accept 成功次数做原子计数；不注入错误、不替换响应、不修改时钟。`epoll_observed_server` 仅在生产事件循环返回后读取 `LoggerStats`，保存日志丢弃数及队列峰值。
- 准备等待连接时，每建立 4 个连接就等待服务器接收完成，避免 backlog 为 5 时的 SYN 重传拖长准备阶段。正式测量按指定并发持续发压。

14 次正常负载测量共校验 **185314 个完整响应**，连接、超时、状态、响应头、正文及尾部数据错误均为 0。各场景结束后 fd 恢复到基线 7 个，健康请求正常，服务器返回 0。

正常场景服务器 CPU 约为单核的 49%～67%，客户端约为 76%～89%；RSS 采样峰值约 3.5～3.75 MiB。256 个等待连接场景的 fd 采样峰值为 312、315。资源每 50 毫秒采样，可能漏掉更短的峰值。

## 满容量与日志

- 保持 1024 个不完整请求连接，再以 16 并发请求 `/health`，分别测量两次。成功 HTTP QPS 均为 0，符合容量拒绝策略。
- 测量窗口分别观察到 20871、22134 次未收到 HTTP 响应的连接关闭。它们属于预期拒绝，不计入成功吞吐量。
- 根据 accept 总数减去受管理连接日志数量，含预热阶段的实际容量拒绝数分别为 24631、25861。日志未丢弃且保留完整，因此可以计算精确数量；限频告警本身只给出拒绝数量的下界。
- 释放等待连接后，正常健康请求通过，fd 恢复基线，服务器正常退出。采样 fd 峰值为 1032、1031；其中包含监听、epoll、信号、日志等描述符，以及接收后立即拒绝的临时 fd，不能直接当作受管理客户端数量。
- 全部 16 次测量的日志丢弃数均为 0；共享日志队列的历史峰值最大为 20 条。

## 结果边界与复现

这些数字是本机、短响应、短连接、固定日志配置下的短时结果。客户端与服务器共享 CPU 和回环网络，Python 发压端及当前 backlog 都可能限制负载；没有测出服务器的极限容量，也没有进行长期稳定性或真实公网测试。

```bash
python3 tests/run_epoll_benchmark.py --report tests/reports/epoll-performance-latest.json
```

可使用 `--duration 10 --warmup 2 --repeats 3` 增加测量时长。原始构建、日志、统计文件在报告的 `artifacts` 目录中；临时目录不保证长期保留，脚本不依赖这次的临时文件。
