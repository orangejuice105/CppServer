# TCP 阶段验收记录

测试日期：2026-10-16（Asia/Shanghai）。完整检查结果：**11/11 通过**。
当前正式配置为 1 个工作线程、1 个排队位置、30 秒收发超时。
服务器通过 CMake 构建，测试未修改服务器源码或正式配置。

## 结果

| 项目 | 实际结果 |
|---|---|
| 连续及分段回显 | 同一连接上的文本、UTF-8、含零字节的二进制、分段发送均逐字节一致 |
| 大数据 | 262144 字节（256 KiB），跨越多次 1024 字节接收，完整一致 |
| 半关闭 | 客户端结束发送方向后仍读到完整回显，随后收到 EOF |
| 排队和拒绝 | A 执行，B 排队，C 被关闭；A 结束后 B 得到回显 |
| 连续连接和资源回收 | 连续连接 40 次，正常路径文件描述符数回到基线 5 |
| 异常断开 | 客户端 RST 触发错误日志，后续连接仍能正常回显 |
| 端口冲突 | 第二进程返回状态码 1，日志记录 EADDRINUSE，第一进程正常回显 |
| 多线程 | 临时 (4,4) 配置副本同时保持 4 个连接，4 个不同工作线程完成回显 |
| 中断与部分发送 | 注入 accept/recv 的 EINTR 各一次、send 的 EINTR 两次；每次最多实际发送 17 字节，5020 字节内容无丢失重复 |
| 接收超时 | 约 30.81 秒结束等待，记录 WARN，后续连接正常 |
| 发送超时 | 缩小测试连接缓冲区、客户端不读响应，约 30.71 秒记录真实发送超时，后续连接正常 |

完整运行后，过载测试进一步固定了准备顺序：先确认 A 已成功回显，再创建 B。
修改后单独复测 `overload`，结果为 **1/1 通过**，避免准备阶段的线程调度差异。

## 验证边界

- EINTR 来自测试辅助库注入，尚未测试真实信号投递、信号处理函数及自动重启语义。
- 部分发送通过测试辅助库限制每次实际发送字节数，覆盖发送循环的偏移和剩余量计算。
- 发送超时使用真实 socket 等待和原配置超时时间；辅助库只缩小缓冲区。
- 多线程验证使用临时配置副本，正式程序仍是 (1,1)。
- 描述符回收只检查本轮正常重复连接路径，不代表所有异常路径都不会泄漏。
- 未做长期压力测试，尚未实现优雅退出；测试清理只终止脚本自己启动的进程。

这份结果作为 TCP 基础阶段的验收记录，后续进入 HTTP 时应继续维护相应验证。
