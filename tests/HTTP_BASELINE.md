## 对应配置与构建

- 4 个工作线程，64 个等待任务位置。
- 接收、发送单次等待上限均为 30 秒。
- 请求头接收有固定 60 秒截止时间，从工作线程进入连接处理起算，不包含排队时间。
  每次接收按剩余预算缩短等待；收到数据和 EINTR 重试不会重置截止时间。
- 该截止时间覆盖请求头接收阶段，响应发送、连接清理仍有各自限制；不是整个处理流程的统一总时限。
- 请求头总上限 8192 字节，请求目标上限 4096 字节；每个连接处理一次请求。
- 连接清理保留 1 秒循环预算、100 ms 单次等待和 64 KiB 字节上限，日志记录结束原因与清理量。
- 全新 CMake 构建，启用标准库断言及未定义行为检测，无编译或运行诊断。
- 直接编译生产源码，测试辅助库仅在子进程映射临时回环端口；报告记录实际测试端口。
- 报告保存构建输入、测试文件和可执行文件的 SHA-256，测试前后输入哈希一致。

## 超限边界与关闭观察

GET 和 HEAD 各测试 4096、4097、8193、16384 字节目标，每个相同字节请求分别一次发送和在目标 4096 字节处分段发送。
GET 的 4096 边界正常进入路由并返回 404，HEAD 返回 405；超过 4096 的上述目标均返回 414。
本轮没有复现超过头部预算的目标因发送方式不同变成 414/431 的差异，没有改动解析/拒绝规则。
当前接收缓冲区是 1024 字节，正常短方法的巨大目标会在接收过程中先触及 4096 检查。

另有 4 项 1 MiB 超长目标检查：GET/HEAD 分别立即读取或延迟 200 ms 读取响应。
全部读到完整的预期响应；日志确认各自额外清理正好 65536 字节即停止，工作线程和描述符正常回收。

本轮客户端 API 观察到 ECONNRESET 的次数为 **0**，另有 **4** 项延迟读取场景的 SO_ERROR 为 EPIPE。
响应完整性、recv 结束方式、SO_ERROR、发送错误、实际发送量和发送/响应时序分别记录，未将传输错误丢弃。
没有抓包，以上结果不能证明整个 TCP 过程没有 RST 包，也不保证任意超预算输入都能收到完整响应。
保留预算，避免通过无限读取来占住工作线程；普通回归仍把可观察复位计为失败。

历史 5 次可观察复位来自加入当前有界清理辅助函数之前的测试，不能直接归因为当前清理预算。

## 复现与边界

```bash
python3 tests/run_http_checks.py
python3 tests/run_http_checks.py --report tests/reports/http-latest.json
python3 tests/run_http_checks.py --only oversize
python3 tests/run_http_checks.py --only request-deadline
```

默认运行全 9 组，三组计时检查并行。部分组或 `--skip-timeouts` 不算完整验收。
报告的 `artifacts` 目录保存原始字节、构建输出、进程输出、日志和独立观察记录；临时目录不保证长期存在。
脚本自己启动的服务器均已停止。资源回收只覆盖列出的场景，未做长期压力测试或 ThreadSanitizer 检查。
EINTR 及指定故障来自注入，没有验证真实信号投递/SA_RESTART。

当前仍不支持非零长度正文解码、成功的 HEAD、keep-alive、静态文件和优雅退出，
没有排队时限及覆盖接收至响应完成全过程的统一截止时间；不将验收解释为完整 HTTP/1.1 实现。
